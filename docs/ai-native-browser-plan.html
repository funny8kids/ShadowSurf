Technical Proposal · 2026 Q4

ShadowSurf：AI 原生浏览器
技术路线与落地方案

本文回答一个问题：在 Atlas 关停、Mariner 退休、Arc 停运之后，一个新团队该用什么技术底座、 什么架构范式、什么产品切口，去做一台真正 AI 原生的浏览器。

调研截止　2026-10-31
覆盖　12 个产品 / 9 个开源项目 / 5 条技术路线
结论　三级火箭：扩展 → 壳 → fork

01核心结论

先给判断，再给依据。五条结论按重要性排序。

01

不要做"通用 AI 浏览器入口"——这条路在 2026 年已被证伪

OpenAI 用 9 个月、Google 用 17 个月、The Browser Company 用整个 Arc 产品线，分别验证了同一件事：用户不会为了"AI 能干活"而更换默认浏览器。留存靠任务完成，不靠浏览习惯。

02

真正的机会是"人机双轨的 Agent 工作台"，不是"更聪明的浏览器"

活下来的产品全部满足一个特征：AI 不是浏览器的主角，而是与你并行的第二个操作者。BrowserOS neo 的"第二浏览器"、Ego Lite 的 Space 隔离、豆包的虚拟桌面，本质是同一件事——给 Agent 一个不打扰你的独立工作区。

03

技术上不要一上来 fork Chromium，用三级火箭

扩展（周级）→ Electron 壳（月级）→ Chromium fork（季度级）。关键不是"选哪个"，而是让同一套 TypeScript UI 与 Agent 逻辑贯穿三个阶段，内核只做胶水。BrowserOS 用这个架构把 90% 代码放在扩展层，fork 只打了少量补丁。

04

能力抽象统一走 CDP，不要绑死任何一个自动化框架

无论底座是扩展、Electron 还是 fork，浏览器能力都通过 Chrome DevTools Protocol 暴露。上层再包一层薄工具集（click / type / snapshot / navigate），这样 Playwright、Stagehand、browser-use 都只是可替换的实现细节。

05

安全与可接管是产品功能，不是合规成本

Comet 靠 BrowseSafe 把注入检测做到 91% 才敢放开自动执行；腾讯 BrowserSkill 把 CAPTCHA/OTP 明确设计成"人工接管"；国内政务采购把"操作可回放审计"列为一票否决项。可回放 + 可中断，是这个品类唯一的信任货币。

三个结构性死因

太重了

独立浏览器要同时扛四件事：渲染引擎、登录态管理、身份授权、分发渠道。这四件事任何一件做不好产品就废，而巨头已经用十亿级主产品把后三件做完了。

留存不成立

"能帮你做事"是功能，不是习惯。用户没有理由为一个偶尔用的功能迁移默认浏览器、重建书签密码扩展。这是 Atlas 用户量起不来的根本原因。

成本结构倒挂

豆包公开的困境极具代表性：2 亿 DAU，日收入不足 ¥100 万，日算力成本数千万。Agent 的每次任务都是真金白银的 token，而浏览器本身不产生收入。

风控墙（中国特有）

极验 Geetest、TLS 指纹、滑块验证码，让无人值守的干净内核寸步难行。这直接解释了为什么中国玩家不做 agent-native 内核，而去做"云机 + 人工接管"。

最重要的反面教材

Atlas 不是技术失败，是定位失败。它把 AI 做成浏览器的主角，于是既没赢过 Chrome 的默认地位，也没赢过 ChatGPT 的使用频次。OpenAI 的最终解法是把能力收回 ChatGPT 桌面端——这说明入口不在浏览器这一层。任何新方案都必须先回答："为什么用户要为一个功能换掉浏览器？"

03五条技术路线

这是本文最核心的部分。市面上所有 AI 浏览器，技术底座无非这五种。选错路线的代价是 6-12 个月。

路线 代表产品 起步成本 能力天花板 主要坑
A. MV3 扩展
Side Panel + CDP		 Nanobrowser、ibl.ai、腾讯 BrowserSkill 1-2 人周 无法改地址栏 / 新标签页 / 内核行为；体验止步于"侧边栏工具" Service Worker 会被休眠；商店审核；chrome.debugger 会显示"正在调试"横幅
B. Electron 壳

C. CEF + 自研外壳 多数企业级浏览器、部分金融终端 2-4 人月 接近 fork 的控制力，但升级只需换 CEF 二进制 C++ 门槛高；CEF 不含 Chrome 内置 AI（Gemini Nano 是 Chrome 私有）；UI 开发慢
D. Chromium fork
真·浏览器		 Comet、Dia、Neon、BrowserOS、Ego Lite、Tabbit 3-6 人月
+ 永久维护		 完全控制：地址栏、新标签页、网络栈、扩展、性能、内置 API 100GB 磁盘 + 数小时编译；每次上游升级要 rebase 全部补丁；必须有 C++ 团队
E. 外部驱动真实 Chrome browser-use、Manus Browser Operator 1 人周 不是浏览器，是 Agent 遥控器；登录态天然复用 依赖调试端口或扩展桥；用户一动就冲突；无法做产品化体验
推荐：三级火箭，而非单选题

三条路线不是互斥的，而是时间上的三个阶段。真正决定成败的架构决策只有一个：把 Agent 逻辑与 UI 写在 TypeScript 层（扩展 / WebUI），内核只暴露 API 和少量补丁。做到这一点，从 A 迁到 B、从 B 迁到 D，都不需要重写业务代码。

BrowserOS 是这个架构最有力的证明：它同时发布"人类浏览器"和"Agent 第二浏览器"两个产品，共用一套 WXT + React 扩展代码；Chromium 侧只有 chromium_patches/ 目录下的少量补丁；Agent 平台是独立的 TypeScript + Rust 服务，跑在 127.0.0.1。

迁移路径

A MV3 扩展
验证场景与成功率 → B Electron 壳
补足体验与 Space → D Chromium fork
补丁 ≤ 20 个 → + WebMCP
站点级工具直连

每一阶段结束时都有一个明确的"继续 / 停止"判据（见第 08 节）。不要在没有验证任务成功率之前启动 fork——这是 Atlas 之外最常见的死法。

04参考架构

六层。自上而下是产品，自下而上是能力。核心设计原则：内核薄、协议厚、UI 可移植。

ShadowSurf 分层架构L5 → L0
L5产品层
侧边栏对话 地址栏 AI 新标签页 Space 双轨 技能库 任务面板 回放时间线
React + Tailwind。扩展形态用 WXT 打包，壳形态用 Vite。同一套组件，两处复用。
L4安全与治理
指令/内容分离 动作白名单 敏感操作确认 域信誉分级 录屏回放 审计日志
不依赖模型"自觉遵守"，而在执行器层面强制约束：支付、删除、发信等动作默认拦截，需二次确认或人工接管。
L3Agent 运行时
Planner Executor Verifier 多 Agent 并行 任务队列 失败重规划
Plan → Act → Observe → Verify 循环。Verifier 是关键：每步执行后做一次"目标是否达成"的判定，避免连续无效点击。
L2上下文引擎
（眼睛）
DOM 简化管道 A11y Tree 截图兜底 跨标签上下文 页面语义索引
参考 browser-use 的五步管道：原始 DOM → 可见性过滤 → 可交互元素标记（编号）→ 结构序列化 → token 预算裁剪。视觉只在 DOM 失效时启用，避免成本失控。
L1能力桥
CDP 薄封装 MCP Server WebMCP Adapter 本地 HTTP/WS
对内有统一工具集（click / type / scroll / navigate / extract / screenshot / wait）；对外通过 MCP 暴露给 Claude Code、Cursor 等任意 Agent 客户端。
L0内核层
Chromium fork / CEF / Electron WebContentsView 扩展 API 网络栈
只做三件事：渲染、提供 CDP、暴露少量自有 API。任何业务逻辑都不下沉到 C++。

一次任务的数据流

指令 自然语言→ Planner 拆成 N 步→ Snapshot DOM+a11y+截图→ 定位 选元素编号→ CDP 执行→ Verify 是否达成→ 重规划 / 下一步

每一步的 snapshot 与动作都落盘，构成可回放的时间线。这既是调试工具，也是企业版的合规卖点。

License 雷区

BrowserOS 是 AGPL-3.0。它的架构值得学，代码不能直接抄进闭源商业产品——AGPL 的网络分发条款会传染。可安全借鉴的是：ungoogled-chromium 的补丁集（BSD）、Chromium 本身的 BSD 许可、以及各 MIT 项目（Midscene.js 等）。如果要做 fork，从 Chromium 官方源码 + 自研补丁起步，而不是从 AGPL 分支起步。

07产品定位建议

ShadowSurf 这个名字其实已经给出了答案：不是"更聪明的浏览器"，是"影子"。

一句话定位

你照常冲浪，影子在另一个 Space 里把活干完。

不做入口，做并行操作者。用户不需要迁移浏览器，只需要在需要干活时叫出影子。

三条产品原则（直接决定架构）

不抢焦点

Agent 的标签页在独立 Space 里，不夺走鼠标、不切换你的当前页。这是 Ego Lite 验证过的第一痛点。

可接管

任意时刻可暂停、可接手、可让人过验证码。国内风控墙决定了"全自动"是伪需求。

可回放

每一步有截图、有动作、有时间线。对内是调试工具，对外是合规卖点，对用户是信任来源。三件事一套实现。

差异化三角

双轨隔离 × 可回放审计 × 成本可见。前两点 Ego Lite 和 BrowserOS 各做了一个，第三点（每个任务花多少 token / 多少钱，实时可见）目前没人做好——而"Cost per Task"已经成为企业采购的正式指标。

切口选择

  • 推荐：跨站信息工作流（多标签调研 → 结构化产出 → 定时监控）。这是 Polar 验证过的方向，任务边界清晰、成功率可度量、付费意愿强。
  • 次选：企业内网/政务的重复性操作。合规审计 + 私有部署 + 信创适配，客单价高，但销售周期长。
  • 避开：通用"帮我订机票"。这是 Atlas 的死因——演示效果极好，真实成功率极低，且直接撞上支付与风控。

08落地路线图

每阶段有明确的"继续 / 停止"判据。没达标就不要进下一阶段——这是控制风险的核心手段。

Phase 0
M1 – M2
形态：MV3 扩展

用最小成本验证"用户真的会让 AI 干活"

  • Side Panel 对话 + 当前页上下文（DOM 简化管道 v0）
  • 三个场景：跨标签调研汇总、表单批量填充、页面变更监控
  • CDP 薄封装（chrome.debugger）+ 动作白名单 + 每步截图
继续判据：任务成功率 ≥ 70%，次周留存 ≥ 25%，单任务成本 ≤ ¥0.5
Phase 1
M3 – M6
形态：Electron 壳

补足体验：双轨 Space + 本地 Agent 服务

  • WebContentsView 多标签 + 垂直标签 + Space 分组（人与影子分离）
  • 本地 127.0.0.1 Agent 服务：持有密钥、跑 Agent 循环、落盘回放
  • MCP Server 端点（让 Cursor / Claude Code 直接调用这台浏览器）
  • 扩展代码整体搬进内置 WebUI，业务层零重写
继续判据：周活用户日均任务数 ≥ 3，任务成功率 ≥ 85%，留存 ≥ 40%
Phase 2
M7 – M12
形态：Chromium fork

拿回内核控制权，补丁控制在 20 个以内

  • 补丁只做四件事：侧边栏容器、地址栏 AI 入口、自有 API 暴露、默认新标签页
  • 跟随 Chromium 稳定版，建立补丁 CI（每次上游更新自动 rebase + 冒烟）
  • WebMCP 适配：站点主动暴露工具时优先走结构化调用，绕开 DOM 解析
  • 扩展完整兼容（这是 fork 相对 Electron 的最大优势）
继续判据：启动速度与内存对齐 Chrome ±10%，扩展兼容率 ≥ 95%
Phase 3
M13+
形态：平台化

从产品到平台

  • 技能市场（用户沉淀的任务模板可分享/交易）
  • 企业版：私有部署、审计日志、Agent 身份标识、数据不出域
  • 按任务计费（Cost per Task）与订阅并行

提示注入 高 网页里的隐藏文本诱导 Agent 转账、泄露 Cookie、删除数据 指令与网页内容物理分离；执行器层动作白名单；支付/删除/发信强制确认；域信誉分级
fork 维护黑洞 高 补丁越打越多，上游一升级全线崩溃，团队被拖死 补丁 ≤ 20 且只做 UI 挂载点；建补丁 CI；Phase 2 之前不许 fork
任务成功率不达标 中 演示惊艳、实际 50%，用户三次失败后永久流失 限定场景边界；公开成功率；失败时给"接管"按钮而不是道歉
国内风控墙 中 极验滑块、TLS 指纹、短信 OTP 让自动化中断 设计人工接管通道；关键站点做适配层；不承诺"全自动"
算力成本 中 每任务多次全页 snapshot，token 成本吃掉毛利 规划/定位模型分离；DOM 裁剪到 token 预算；本地小模型跑元素定位；缓存页面结构
License 传染 低 误用 AGPL 分支导致闭源产品被迫开源 只借鉴架构不抄代码；从 Chromium 官方 + BSD 补丁起步
