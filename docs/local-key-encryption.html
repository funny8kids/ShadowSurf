本机密钥 与环境可迁移性

你的环境指纹由一把本机密钥保护。这一页说清三件事：谁能打开你的环境、换电脑会发生什么、以及你该怎么把环境带走。

01这件事解决什么

每个环境（Profile）的指纹不是随机生成的，而是由一把密钥推导出来的。推导规则固定：同一个环境永远得到同一套指纹，换一个环境得到完全独立的一套。

这把密钥叫 master.key，存在本机的数据目录里，由操作系统按当前登录的 Windows 账号 + 这台电脑加密。它带来两个后果，一好一坏：

  • 好处：别人把你的数据目录整个拷走，在他的电脑上打不开——因为他没有你这台电脑的解密能力。
  • 代价：你的电脑重装系统、或换一个 Windows 账号登录，你自己也打不开了。这时所有环境的指纹会重新生成成另一套。

这一页的大部分内容，都是在处理那个「代价」。

02你会看到什么

场景环境能不能打开界面会告诉你什么
同一台电脑、同一个 Windows 账号 能　指纹与上次完全一致 无提示。这是默认情况，应当「什么都没发生」
换一台电脑 不能 环境列表照常显示，点开时提示「这个环境属于另一台电脑」，并给出「用导出包恢复」的入口
同一台电脑、换一个 Windows 账号 不能 同上。系统不区分「换机」和「换账号」，两者都算「不是原来那个人」
重装系统 不能 同上。这是最容易发生的一种，务必提前导出
手动删掉 master.key 能打开，但指纹变了 打开时提示「环境指纹已重新生成，与历史记录不一致」。不是环境消失，是变成了另一套指纹
用导出包在新电脑上导入 能　指纹与导出时一致 输入导出时设置的口令，解开后环境列表恢复

03三句你能自己验证的话

下面的三句话是这一页的核心。如果哪一句和你看到的不一样，那就是 bug，请报给我们。

#你看到的这意味着
1 同一台电脑、同一个 Windows 账号，所有环境照常打开，指纹和昨天一样 加密没有影响正常使用。这是最重要的一句——加密功能最常见的线上事故不是被攻破，而是用户自己的数据打不开了
2 换电脑 / 换 Windows 账号 / 重装系统后，环境打不开，并且界面明确说「这个环境属于另一台电脑」 不是报错、不是崩溃、不是列表变空。一个说得清的拒绝，比一个说不清的失败有用
3 删掉密钥文件后，所有环境的指纹会全部换成另一套 注意：是「变了」，不是「消失了」。这两种后果完全不同，别当成环境报废

第 3 句值得多说一句：很多人以为删掉密钥等于「环境没了」，于是把还能用的环境也一起删掉。实际上环境还在，只是它变成了另一个身份——对平台来说，这等于换了一个人。所以删密钥是一个「不可撤销的身份变更」，不是一个「清理动作」。

04换电脑、重装系统怎么办

提前做一次导出。导出包用你自己设的口令加密，口令不存本机、不上传，忘记就无法恢复。

本节的实现状态说明
未实现 对用户来说这条路径不存在——没有 IPC、没有界面。但要说准：口令封装的核心已经写好了（src/main/core/portable-seed.ts，scrypt N=2^15 → AES-256-GCM，已有往返、错口令、篡改三组测试），缺的只是接线。本节描述它落地后的行为，与 P0-3 同批交付、同批发布。在此之前，换机或重装系统会导致环境指纹全部重新生成且无法恢复——这一点必须在应用内提前告知用户，不能只写在这份文档里。
步骤做法
导出在「数据」页选择要带走的环境 → 导出 → 设置一个口令 → 得到一个环境包文件
保管把环境包和口令分开存放。放在一起等于没加密
恢复在新电脑上：导入 → 输入口令 → 环境列表与指纹恢复到导出时的状态（这句话成立有前提，见下一节）

环境包里必须装什么

上面那句「指纹恢复到导出时的状态」是有前提的，而这个前提现在还没被任何代码保证。它决定了这个包到底能不能把身份带走：

内容必须带不带的后果
seed 必须 没有它就没有身份可恢复
存储下来的那份 fingerprint（含你手动改过的项） 必须 只带 seed，导入方就只能用 seed 重新算一遍指纹。算出来的是不是原来那个身份，取决于两件不受你控制的事：算法版本有没有变、你当初有没有手动调过分辨率或 UA。应用能打开，但它是另一个人——而界面上不会有任何提示
代理、Cookie、脚本等业务数据 可选 与身份无关，属于另一个包，单独决定带不带
这不是理论风险，是设计上的岔路

生成指纹的函数有三个入参：系统、seed、你手动改过的那些项（buildFingerprint(os, seed, overrides)）。第三项推不出来——它不写在 seed 里。所以「只带 seed 的包」在导入时只有两条路：

一是重算，指纹可能变；二是包里额外带上那份指纹，原样写回。没有第三条路。本页按第二条写，因为第一条的失败是静默的，而静默的身份变化正是这个产品最不能犯的错。

为什么不用「登录账号同步」来解决这件事：那意味着密钥要经过我们的服务器，而这个产品的承诺是数据不出本机。用口令加密的导出包，是「不上传、又能带走」的唯一做法。

05加密不可用的时候

少数情况下，操作系统不提供加密能力（例如某些精简版系统、或远程会话环境）。这时程序不会假装一切正常：

状态密钥怎么存界面显示
正常系统加密后存储无提示
加密不可用明文存储设置页与环境列表常驻提示：「本机加密不可用，密钥以明文存储」。不会只在日志里写一行

这条规则和「指纹伪装失败时必须标红」是同一条：降级必须留痕。用户有权知道自己的环境此刻处于什么保护水平。

06我们不承诺什么

不承诺原因
「数据绝对不会被读到」本机加密保护的是「目录被拷走」这一种情况。如果攻击者已经能以你的账号登录这台电脑，他能做的不止读密钥
「忘记口令还能找回」口令不存本机也不上传，没有任何找回通道。这是设计选择，不是缺陷
「换机后环境自动恢复」恢复需要你手里的导出包和口令。没有它们，任何一方（包括我们）都无法重建你的环境
「加密等于环境不可伪造」加密保护的是存储。指纹是否被目标网站识破，是另一件事，见架构文档的「指纹一致性」一节

07验收口径（四条）

这四条缺一不可。只满足第 2 条的实现会被判「通过」而实际没修好——这是本仓库已经发生过一次的假绿。

#口径判据为什么必须有这条
1 无残留 数据目录内不存在任何含明文 seed 的文件，包括 profiles.json、迁移备份 .schema<N>-*、崩溃前字节副本 .corrupt-*、.preupgrade* 只加密 profiles.json 而备份里还躺着同一批明文 seed，等于没修。备份文件让「不可重建」这条判据自动失效——攻击者不需要重建，seed 就在那里
2 不可重建 删掉 master.key 并把数据目录搬到另一台机器，seed 不可重建 这是加密的本意。注意它是安全判据，不是产品判据——单独用它验收会漏掉第 1、3、4 条
3 合法路径可用 加密前后各取一次快照，四个值逐字相同：navigator.userAgent、screen.width×screen.height、Intl.DateTimeFormat().resolvedOptions().timeZone、navigator.language。任一不同即不通过——应用能打开不算通过 最容易被加密改坏、且现在无人测的一条。加密功能最常见的线上事故不是被攻破，是用户自己的数据打不开了。「解密链路正常」不是判据——它无法被观察，只能被声明
4 降级可见 safeStorage 不可用、或任一处回退到明文时，界面必须常驻显示，不得只写 console.warn 静默降级让用户以为自己处于保护状态。与「指纹伪装失败必须标红」是同一条规则

口径 3 怎么验

「逐项一致」不是一句能直接执行的话，因为不先记录就没有可比对象。这条口径分三步，少一步就退化成「看起来能打开」：

步做什么这一步为什么不能省
1加密之前，逐个环境打开一个空白页，把上面四个值抄下来存成文件不存基线，第 3 步就只剩「能打开」。加密最典型的失败不是打不开，是打开了但身份变了——而这种变化界面上不会有任何提示
2启用加密，完全退出应用再重开进程内的缓存会让「没真正读盘」也显示正常。必须重开，才能证明读到的是加密后的文件
3逐个环境再取一次同样四个值，与基线逐字比对差一个字符就判不通过。这里不看「像不像」，只看「是不是同一串」
基线的时效

第 1 步的记录必须发生在加密动作之前。事后补录的基线不成立——那时候已经没人知道原值是什么，比对就变成了自己和自己比。

同理，已经开启加密的环境补不出这条证据。这不是流程上的麻烦，是这条口径唯一有鉴别力的形式：它证明的是「变化没发生」，而不是「现在看起来没问题」。

08门禁与复现

命令实际覆盖不覆盖
npm run verify:seed-at-rest 口径 1 的全部（全目录扫描，含备份与字节副本）；口径 2 的前半——明文既然不存在，删掉密钥就没有可重建的东西 口径 2 的后半（要真把目录搬到另一台机器才算验过）、口径 3、口径 4
npm run test 口令环境包的加解密往返（sealSeeds/openSeeds）；enc: 形态与 schema 校验规则 DPAPI 那条 sealSeed/openSeed 没有任何测试——它在 tests/ 里零引用，只有 tools/probe-seed-seal.mjs 这个手工探针；也完全不覆盖「指纹是否与加密前一致」
npm run verify:all 以上全部 + 注入与反检测门禁 同上。它不会因为多跑了几个套件就多覆盖一条口径
门禁全绿 ≠ 四条口径都过了

口径 3 和口径 4 目前没有任何自动门禁，只能人工按上一节的三步做、以及在降级时看界面。把它们写成「由某个命令覆盖」，会让一次全绿的运行被读成「四条都验过了」——而这正是本仓库已经吃过一次亏的那类假绿。

更具体地说：把明文 seed 变成 enc: 再变回来的那两个函数（src/main/store/seed-seal.ts）现在一条测试都没有。它们是这条功能的正中间，两侧都有测试，中间是空的。

口径 1 的措辞比门禁窄，这一点要先对齐

口径 1 写的是「明文 seed」，而门禁报的是「明文凭据」——它把 local-api-token.json 的 token 也算进来了。这个差异不是猜的，工具自己的开头就写着「不得有明文的 seed / token / 密钥」（tools/verify-seed-at-rest.mjs:5），比口径 1 的措辞宽。两个范围不一致会有两种结局，两种都不好。

一是照文档做完（清掉那 3 条 seed）门禁仍然红，于是有人去改门禁的扫描范围让它变绿——那是改测试，不是修数据。二是反过来，认为 token 不属于这条口径而放过它——而它和 seed 泄露的后果同类：拿到它就能以本机身份调用本地接口，并且它同样会在「目录被拷走」时一起被拷走。锁了前门留着后门，不叫修好。

本页暂按「明文凭据」这个更宽的范围描述，等这一条定稿后再发布。

这个数字会变

上面的读数是某一刻的快照，不是结论。红灯的过期速度比绿灯快——有人正在修，你看到的时候可能已经是 0，也可能因为新写入的文件又变多。

要当刻的读数，跑一次 npm run verify:seed-at-rest，不要引用上面的数字。
